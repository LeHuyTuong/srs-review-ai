# AGENTS.md — srs-review-ai

Công cụ chấm chất lượng tài liệu SRS bằng LLM: app Flutter đọc file SRS, tách từng requirement, gửi lên server FastAPI, server gọi Gemini chấm theo rubric. Tài liệu mẫu dùng để thử là OTES SRS.

Repo 11 commit, hai ngôn ngữ trong một cây và **không dùng chung build**.

## Bố cục

```
app/        Flutter (dart sdk ^3.12.2, package `srs_review_ai`) — UI + tách requirement
server/     FastAPI + Gemini — chấm điểm, cache, rate limit
contracts/  review.schema.json + fixtures — hợp đồng giữa hai bên
docs/       adr/ (0001–0008, chỉ mục ở adr/README.md), evidence/, plans/, roadmap.md, tech-lead-brief.md
tools/      check_guardrails.py, install-hooks.sh
review-rules/  bộ luật chấm SRS/SDS model-agnostic (RULEBOOK.md là nguồn sự thật) — xem README trong đó
skills/     Claude skill srs-reviewer / sds-reviewer — LOCAL, đã ignore, không theo dõi trong repo; vẫn là adapter mỏng trỏ về review-rules/
reviews/    ledger chạy thật trên tài liệu có sẵn (OTES, HisWise, CarbonX) — bằng chứng hiệu chuẩn thang điểm
```

`docs/adr/` và `docs/evidence/` là nơi ghi quyết định và bằng chứng; đọc trước khi đổi luật chấm. Hai file phải đọc trước khi động vào engine chấm: **`docs/plans/7-review-engine-v2-2026-09-15.md`** (kết luận rút từ 4 lần chạy thật: đơn vị output của app sai, 8 check giá trị nhất đều thuần text, workflow hai pass) và **`docs/adr/0008-kiraai-provider-evaluation.md`** (vì sao không thêm KiraAI làm provider).

**Luật chấm mới thêm vào `review-rules/`, không vào code hay prompt trước.** Muốn port một luật vào app: tra `review-rules/adapters/app-port-map.md` xem nó đã có `CheckId`/`DiagramType` chưa và thuộc tầng nào.

## Chạy và test

```sh
# Server — pytest KHÔNG có trên PATH, chỉ có trong venv
# (cwd = thư mục gốc repo srs-review-ai/, KHÔNG phải cha nó)
cd srs-review-ai/server && .venv/bin/python -m pytest tests/

# App
cd app && flutter test        # 10 file *_test.dart
```

**`python3 -m pytest` luôn trả `No module named pytest`.** Python hệ thống không có nó; toàn bộ dependency nằm trong `server/.venv` (Python 3.11). Mọi con số "37 test đã pass" trong docs chỉ đúng khi chạy qua venv — gọi `pytest` trần rồi kết luận "test hỏng" là chẩn đoán sai.

**`ruff` không có trên máy này nhưng CI chạy `ruff check .` + `ruff format --check .`** (`.github/workflows/ci.yml`). Đừng mất thời gian cài local; để CI báo.

**`tools/check_guardrails.py` thi hành 7 nhóm luật** (CI + pre-commit qua `tools/install-hooks.sh`): secrets, app không gọi thẳng LLM, MVVM layering, dependency pins, contract version, design tokens, và **native plugin** — `pdfx` / `path_provider` / `file_picker` / `shared_preferences` chỉ được import trong file đã đăng ký ở `NATIVE_PLUGIN_RULES`, mỗi đăng ký kèm seam (probe, fake inject, conditional stub) mà script kiểm lại từng lượt: import ở file chưa đăng ký thì fail, xoá seam cũng fail, đăng ký còn mà file không import nữa cũng fail. Muốn thêm call vào một plugin native: đặt nó sau seam rồi đăng ký file đó trong script — **đừng thêm ngoại lệ**. Viết pattern seam đừng bám vào một dòng: `dart format` xếp lại typedef dài là pattern một dòng đã mục (lỗi đầu tiên của chính luật này, bắt được nhờ probe 3 đường fail trước khi commit).

- **Retry storm: app và server cùng retry một lượt → 1347 call Gemini cho 238 unit (đã vá 2026-09-22, đã commit: 9527aa7 pacing + 7779632 batch).** Lượt OTES thật đốt 1347 call upstream, 1109 bị từ chối (582×429 model chính + 522×429 và 503 của model fallback), trong khi chỉ 238 unit có kết quả. Ba nguyên nhân cộng lại: (1) app gửi 1 call/unit, 4 luồng song song; (2) `GeminiProvider` backoff cứng 1s/2s/4s **không jitter**, 3 lần × 2 model = tối đa 6 call cho một unit xấu, mọi worker retry cùng nhịp (thundering herd); (3) app coi 502 là `isRetryable` rồi retry 3 lần nữa trong khi server đã thử hết. Bản vá: `server/app/llm/pacing.py` (`ProviderPacer` **toàn cục theo tiến trình** — `build_provider()` chạy mỗi request nên pacer không thể nằm trên instance provider) token-bucket 12 call/phút + burst 4, đọc `retryDelay`/`Retry-After` của Google làm cooldown (**cooldown theo model**: quota Google là theo model, chặn cả fallback là tự bắn vào chân; 503 cooldown toàn bộ), jitter mọi lần chờ, và trần `provider_max_cooldown_s` cho tổng thời gian một request được phép ngủ (phải < 90s timeout của app, nếu không app timeout rồi retry chồng lên throttle); app bỏ retry 502 (`503` vẫn retryable); và **`POST /review/batch`** gộp 6 unit văn bản thành 1 call (238 unit → ~40 call). Đo: 1347 → ~240 (A) → ~40 (A+B). Ba luật phải giữ khi động vào phần này: (a) **mọi call upstream phải đi qua pacer** — thêm `provider.generate_json` ở chỗ khác mà quên `acquire` là tái tạo storm; (b) **unit có ảnh trang không bao giờ vào batch** (`/review/batch` chỉ nhận text, `planReviewTasks` xếp chúng đi riêng một mình); (c) **502 ở tầng app nghĩa là server đã retry xong** — retry thêm ở client chỉ nhân tải lên. Batch trả 200 kèm `failed[]` thay vì 502 toàn bộ để client giữ phần đã trả tiền (cache ghi theo từng unit, chạy lại miễn phí). Proxy cũ không có endpoint này trả 404 → repository tự lùi về 1 call/unit và ghi nhớ cho cả lượt (hồi quy: `app/test/review_repository_batch_test.dart`, `server/tests/test_pacing.py`, `server/tests/test_batch.py`). **Sau khi kéo code này phải restart proxy** — uvicorn cũ trả 404 cho `/review/batch`.

- **`pdfx` (renderer ảnh trang) là plugin native pdfium — chết cứng trong mọi test runner trên host**, với hai thông điệp đánh lạc hướng lần lượt: `Binding has not yet been initialized` (thiếu test binding) rồi `PlatformException(channel-error, Unable to establish connection on channel)` (vẫn không có channel thật). Đã mất ba lượt debug vì mỗi lỗi trông như một bug khác nhau (audit fail, proxy fail). Cách đúng: raster bằng `pdftoppm` trên host vào file, inject qua `renderPage` giả để đo chuỗi service→proxy; đường render thật chỉ test được on-device (QA sign-off đã làm).
- **Bẫy nối tiếp của `pdfx`: `PdfDocument.openData` gọi `assertHasPdfSupport()` mà KHÔNG await, nên verdict "nền tảng không hỗ trợ" rơi ra như unhandled async error và xuyên qua mọi `try/catch` (đã vá 2026-09-24, commit bf44431).** Bug nằm trong chính pdfx-2.11.0 (`lib/src/renderer/interfaces/document.dart`: `openData` vứt future của `assertHasPdfSupport`; `hasPdfSupport()` trả `false` trên Linux), không phải code repo sai. Triệu chứng: Job App (Ubuntu) đỏ đúng một test, annotation công khai `app/test/workspace_view_model_test.dart :: vision audit wiring audit rows reach the session a reopen reads :: PlatformNotSupportedException: Actual platform not supported by it method, try use another`, trong khi cùng suite chạy trên máy Windows xanh (838 pass). Vì future bị vứt chứ không bị await, hai nhánh "degrade to text-only" đã dựng sẵn — `render-failed` trong `ReviewRepository._drive` và `failures.add` trong `VisionReviewService.audit` — **không bao giờ chạy**: không có `await` nào ném thì `catch` không có gì để bắt, lỗi rơi vào zone của flutter_test và bị gán cho test đang chạy. Cách đã chứng minh (không phải suy luận): một probe tạm vứt một future fail bên trong `try` cho ra đúng thông điệp của CI kèm `===== asynchronous gap =====`. Fix: `PageImageRenderer` nhận `PdfSupportProbe` (`Future<bool> Function()`), hỏi `hasPdfSupport()` trước rồi mới `openData`, và ném `PdfRendererUnavailable` (subclass của `UnsupportedError` nên mọi caller cũ vẫn bắt được như thường) — await được, không còn rơi vào zone; phía test thì inject renderer giả (`_FakePageRenderer`) thay vì để pdfx tự phán. Degrade im lặng vẫn làm lượt chấm trông như đã chấm sơ đồ, nên coverage giữ cờ riêng `rendererUnavailable` (reason `no-pdf-renderer`, **không** gộp vào `render-failed`) và summary bar + toast + tab Findings nói thẳng một dòng "no PDF renderer — the diagrams were reviewed from text only". Luật: **mọi call vào plugin native phải có probe hoặc fake để "nền tảng không hỗ trợ" thành lỗi bắt được — đừng trông vào `try/catch` quanh call đó.**

- **PDF: ảnh nhúng KHÔNG giữ file PNG gốc — `mxfile` của draw.io không bao giờ sống sót trong PDF.** Image XObject chứa *raw samples*; mọi producer (Word, LaTeX, print-to-PDF) đều bỏ chunk phụ như `tEXt`/`iTXt`, và `doc.extract_image()` của PyMuPDF **encode lại** thành PNG mới. Hệ quả: bộ scan mxfile trong `server/app/docmap.py` vẫn phải giữ (nó dùng thật cho `word/media/*` của DOCX, nơi file gốc còn nguyên) nhưng **đừng kỳ vọng nó bật trên PDF** — test đúng cách là test ở tầng bytes (`_scan_embedded`), không phải nhúng PNG vào PDF rồi assert `readable == "mxfile"` (lần đầu viết test như vậy và nó fail đúng như lý thuyết).
- **`page.get_drawings()`: rect zero-width bị coi là `is_empty`, và khung viền trang nuốt cả trang.** Hai cái bẫy cùng nằm trong một hàm gom cụm (`_cluster_drawings`): (1) đường nối (connector) có rect rộng 0 → `is_empty == True` → lọc theo `is_empty` là **mất hết mũi tên**, mà mũi tên chính là thứ giữ sơ đồ UML lại với nhau; phải inflate 1pt, không phải bỏ. (2) một path phủ ≥95% trang (page border) *chứa* mọi rect nội dung → gom cụm trước rồi lọc coverage thì cả trang thành 1 cụm rồi bị xoá sạch → phải loại khung viền **TRƯỚC** khi gom. Cả hai lỗi đều lộ ra qua test fixture tự dựng bằng PyMuPDF (12 path → phải ra đúng 1 region), không lộ qua đọc code.
- **`context_text` của `/diagram` bị cắt ở 4000 ký tự.** Muốn nhét nguồn draw.io/ngữ cảnh "có thẩm quyền" vào prompt thì phải để **lên đầu** và tự cap (client cắt 2400), nếu không phần bị cắt mất chính là phần đáng tin nhất.
- **Thêm một provider đọc lúc import có thể làm nổ test cũ.** `documentMapServiceProvider` đọc `proxyUrlProvider` → `sharedPreferencesProvider` (chưa override trong `flutter test`) → `ProviderException` giữa `importDocument`. Hai luật: (1) trong VM, `ref.read(provider)` phải nằm **trong** `try` (một tiện ích phụ không được phép biến import tốt thành lỗi); (2) harness test (`_container` trong `workspace_view_model_test.dart`) override provider mới về `null` mặc định, và truyền fake khi cần đo đường mới. Cùng lớp lỗi này cũng gặp khi override `ReviewRepository.run` trong test subclass — thêm tham số mới vào signature là phải thêm ở mọi subclass.
- **Lịch sử đánh giá "biến mất" mỗi lần `flutter run -d chrome` — dữ liệu KHÔNG mất, chỉ nằm ở profile Chrome khác** (2026-09-25). `flutter run -d chrome` không dùng `app/.dart_tool/chrome-device`; nó tạo profile tạm mới mỗi lần ở `%TEMP%\flutter_tools.<hash>\flutter_tools_chrome_device.<hash>\`, **kèm port ngẫu nhiên**. Trên web lịch sử nằm trong IndexedDB, mà IndexedDB gắn với **origin (host:port) của profile đó** ⇒ lần chạy mới = origin mới = DB rỗng, dù profile cũ vẫn nằm nguyên trên đĩa (đo được: profile cũ 235,8 KB có chuỗi `OTES`, profile mới 4,1 KB). Cách phục hồi đã dùng: giữ **cùng origin** (`localhost:54613`) và copy `Default/IndexedDB` sang profile cố định `%LOCALAPPDATA%\srs-review-ai\chrome-profile`. Cách phòng tái diễn: chạy `powershell -ExecutionPolicy Bypass -File app\tool\dev_web.ps1` (port cố định + profile cố định, `flutter run` vẫn ở foreground nên còn hot reload). **Đừng** dùng `flutter run -d chrome` khi đang có phiên đánh giá thật trên web; nếu buộc phải dùng thì copy profile sang vị trí cố định trước, và nhớ IndexedDB không di chuyển được sang origin khác.
