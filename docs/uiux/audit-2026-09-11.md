# UI/UX audit — measured, 2026-09-11

Scope: the Flutter app in `app/`, driven in a phone viewport (393 × 852, DPR 2,
touch) in headless Chromium against the live release build at
`http://127.0.0.1:8443`.

Commissioned by: *"app hiện tại khá chậm… nó đang process ko hiện, ko thân thiện
với user lắm đâu bắt users đợi, ko báo cáo tiến độ, rồi thì phải bấm menu chưa
ổn lắm… làm uiux giống cái glass của iphone 17 ấy ios 26."*

Everything below is a measured number or a quoted code line. Where a claim is a
judgement rather than a measurement, it says so.

---

## 1. How this was measured

Flutter web renders to canvas, so there is no DOM to read. The app already
carries a dev-only hook in `lib/main.dart:17` that turns on Flutter's semantics
tree when the URL contains `?smoke=`. The tour drives that tree.

Reusable harnesses, all committed alongside this report:

| File | What it does |
|---|---|
| `app/tool/uiux_tour.py` | Full walkthrough: cold load → demo → tabs → import → review → ask. Records timings, tap-target geometry, console errors, screenshots in `/tmp/uiux/`. |
| `app/tool/uiux_review_probe.py` | Starts a review through its real button and samples the screen every 150 ms while it runs. `--demo` runs the 63-unit path. |
| `app/tool/uiux_recon.py`, `uiux_probe_nav.py` | Label/geometry reconnaissance. |

**One harness bug, recorded because it changed a number.** Flutter's semantics
nodes are absolutely positioned DOM, but a raw `mouse.click(x, y)` at a
coordinate outside the viewport silently clicks nothing. The first run tapped
"Run review" while the button sat below the fold (`y=1687` in a 852 px
viewport), so the review never started and the probe reported a 150 s "hang".
The corrected harness tags the target node and lets Playwright scroll it into
view first, exactly as a human thumb would. The numbers below are all from the
corrected harness. **The first false result is worth remembering: an unclickable
control is indistinguishable from an app that ignores you.**

Environment note: nothing listens on `localhost:8000`, so every run logs 9 ×
`ERR_CONNECTION_REFUSED` while the rubric fetch falls back to the committed
copy. That is the app's intended offline behaviour, not a defect.

## 2. Verdict on the four complaints

| Complaint | Verdict | Measured evidence |
|---|---|---|
| "khá chậm" (feels slow) | **Partly true, and the wrong problem is being felt.** Time-to-first-shell is good; it is the *review run* that is enormous. | Cold load → canvas **1032 ms**, → shell text **1039 ms** (canvaskit.wasm 696 ms of it). Demo load → 65 units listed in **353 ms**. Bottom-tab switch **3 ms**. Import modal open **103 ms**. Real `.docx` (1.4 KB, 8 units) parsed in **1958 ms**. But a **63-unit mock review ran past 120 s without finishing**. |
| "process ko hiện" (no visible processing) | **TRUE — confirmed, and it is a UI defect, not a performance one.** | During the 63-unit run, sampled at 5 s / 15 s / 30 s / 45 s, the screen is **identical** to before the run: `Cancel` absent, stage label absent, percentage absent. The only `[role=progressbar]` on screen reports `aria-valuenow="97"` — the *static* "97 % whole use-case context" inventory bar. |
| "ko báo cáo tiến độ" (no progress reporting) | **TRUE — the progress UI exists but is unreachable.** | `workspace_modals.dart:294-313` renders the stage label, `LinearProgressIndicator` and `Cancel` inside the modal. `workspace_modals.dart:316-321` then calls `Navigator.of(sheetContext).pop()` *before* `await viewModel.runReview()`, destroying that UI before it can ever show a frame. `workspace_shell.dart` contains **zero** references to `isRunning` or `progress`. |
| "phải bấm menu chưa ổn" (too many menu taps) | **Only partly true.** | Bottom nav is **one tap** and switches in 3 ms. Frequent destinations are cheap. The real cost is that review progress and the review history are only reachable *through* a modal you must re-open, and the modal is where "Run review" lives — 2 taps to re-run, 1 to discover there is no way to watch or cancel a run already underway. |

**Bottom line: the app is not primarily slow — it is silent.** The one genuinely
slow operation (the review) is also the one operation with no progress, no
label, no percentage and no cancel. That combination is what reads as "bắt users
đợi".

## 3. Findings, by severity

### P0 — the review run is silent, uncancellable and over the cap

**P0-1 · Progress is destroyed the moment the review starts.**
`app/lib/features/workspace/view/workspace_modals.dart:316-321`

```dart
onPressed: state.selectedCount == 0
    ? null
    : () async {
        Navigator.of(sheetContext).pop();   // <-- sheet (and its progress UI) is gone
        await viewModel.runReview();
      },
```

The `if (state.isRunning)` block at lines 294-313 is the only place in the app
that renders review progress. Popping the sheet removes it. Nothing in the shell
takes over.

**P0-2 · The user waits with a screen that has not changed.**
Measured: at 5 s, 15 s, 30 s and 45 s after start —
`has_cancel=false`, `has_progressbarlabel=false`, and the sole progressbar on
screen is the static inventory bar at `aria-valuenow=97`.
The README's own promise is "emits `ReviewProgress` so the UI can show real
stage labels **instead of a spinner**" (`review_repository.dart:3-4`) — the app
shows neither.

**P0-3 · Review runs strictly sequentially, so it scales linearly with the document.**
`app/lib/data/repositories/review_repository.dart:106-141` — a `for` loop with
`await _api.review(...)` per requirement. No concurrency, no batching. Per-call
`receiveTimeout` is **90 s** (`app_config.dart:41`), so a 40-unit online run has
a worst case in the *hours*, with a UI that reports nothing.

**P0-4 · The demo advertises more units than it reviews, silently.**
`MockReviewApi` latency is **350 ms per requirement** (`mock_review_api.dart:14`)
and `AppConfig.maxRequirementsPerRun = 40` (`app_config.dart:48`). The demo
loads 65 units and the button reads **"Review 63 units"** (measured), but the
repository does `.take(40)`. **23 units are dropped with no message.** This
directly contradicts the product's central claim — "No silent truncation",
"Những gì không khớp quote? Nó không được lọt vào" — and the app's own copy:
*"nothing will be silently skipped"* (`workspace_view_model.dart:250`).
The repository's own docstring (`mock_review_api.dart:44`) reads
*"Kept non-zero so progress indicators and cancellation stay demonstrable"* —
the latency exists specifically to make progress visible, and the UI makes it
unreachable.

### P1 — feedback and affordance gaps

**P1-1 · Tap targets below the 44 px platform minimum.** 12 measured button
targets, phone viewport:

| Target | Size | Where |
|---|---|---|
| Progress stepper "Import / 2 Inventory / 3 Findings / 4 Export" | **69×21, 89×21, 80×21, 69×21** | header, `y=218` |
| "Document information", "Replace document" | **34×34** | document card |
| "Ask document" | 40×40 | header |
| "Previous page", "Next page" | 40×40 | inventory pager |
| "Run review", "Import document", "Export report" | 40 tall | main actions |
| "Change", "How verification works →", "Inspect flagged units →" | **16 tall** | body links |
| Malformed-ID chips `UC0134`, `UC0114` | 50×23 | attention card |

Apple's minimum is 44×44 pt; the stepper at 21 px and the 16 px text links are
roughly **half** the minimum. The main actions at 40 are marginal.

**P1-2 · No cancel affordance anywhere reachable.** `cancelReview()` exists
(`workspace_view_model.dart:363`) and the repository implements cancellation
cleanly via `CancelToken`, but the only button bound to it is inside the popped
sheet. The user cannot stop a run they can see is going nowhere.

**P1-3 · The "Run review" button keeps a stale label while running.** `onPressed`
is correctly disabled (`inventory_tab.dart:275`, `findings_tab.dart:50`) but the
label never changes to "Reviewing…" or shows a spinner, so a disabled button on
an otherwise frozen screen is the only state signal.

**P1-4 · No elapsed time or estimate.** Nothing in the app shows how long a run
has been going or how long remains. For a 63-unit run that can exceed two
minutes, this is the difference between "working" and "hung".

### P2 — polish and consistency

**P2-1 · Import parse is fast but unlabelled.** The real `.docx` path shows a
progressbar within **452 ms** and completes in **1958 ms** — acceptable, but
there is no stage text ("Reading file…", "Splitting requirements…" exists in
`ReviewProgress.label` but is never rendered during parse).

**P2-2 · Duplicate font loading.** `Manrope.ttf` and `DMSans.ttf` are each
fetched twice (measured), ~400 KB of avoidable transfer on a cold load.

**P2-3 · Stepper semantics are cramped and unlabelled as a group.** The four
nodes expose concatenated text (`"Import2 Inventory3 Findings4 Export"`) to the
accessibility tree; screen-reader users get one run-on string.

**P2-4 · The document card claims page counts the demo did not parse.**
"114 pages · 27.37 MB · Extraction complete" is synthetic demo metadata. Honest
for a synthetic fixture, but it is indistinguishable from a real parse result
and would be dangerous if a real file ever failed and left demo metadata on
screen.

## 4. What is already good — keep it

- **Cold start is fast for a canvas app**: 1039 ms to first shell text, with no
  flash of unstyled content.
- **Navigation is instant**: bottom tabs switch in **3 ms**; the inventory
  paginates over 65 units without a hitch. The "menu" complaint is not about
  speed.
- **Offline degradation is genuinely graceful**: 9 proxy connection failures
  produced **zero** user-visible errors — the run falls back to mock mode and
  the rubric falls back to the committed copy.
- **Honest error copy throughout** (`api_service.dart._translate`) — messages
  are written for the person at the screen, not for a log file. That is rare
  and should be preserved.
- **The evidence discipline is real**: `dropped_issue_count`, verbatim-quote
  verification, and preserved malformed IDs are all implemented, not marketed.

## 5. Fix plan

Ordered by value per unit of risk. Each item carries its acceptance criterion.

### P0 — do these first

1. **Move review progress into the shell** — the single highest-value change.
   In `workspace_modals.dart:316-321`, do not pop the sheet until the run has
   reported its first progress event; render a persistent progress surface in
   `workspace_shell.dart` (a glass bar under the header, or a bottom sheet that
   survives the run) bound to `state.progress`.
   *AC:* during a 63-unit mock run, a stage label and a determinate bar are
   visible within 500 ms and update at least once per requirement; `Cancel` is
   tappable throughout.

2. **Surface the cap honestly.** Either raise `maxRequirementsPerRun` to match
   the demo, or state the cap before the run and report the skipped count after
   it.
   *AC:* no run ever reviews fewer units than the button's stated count without
   an explicit, visible message naming the number skipped.

3. **Add bounded concurrency** to `ReviewRepository.run` (a worker pool of 3–4,
   preserving per-item failure isolation).
   *AC:* a 40-unit online run completes in roughly a third of the sequential
   wall time, with progress still monotonic.

4. **Show elapsed time and a rough estimate** next to the bar, and keep
   `Cancel` bound to `cancelReview()`.
   *AC:* elapsed time is visible and increments at least once per second.

### P1

5. **Raise every interactive target to ≥44×44** — the 21 px stepper, the
   16 px text links, and the 34×34 icon buttons first.
   *AC:* the tap-target scan in `uiux_tour.py` reports zero buttons under 44 px.

6. **Give "Run review" a live label** ("Reviewing 12/40…") and an inline
   spinner while `state.isRunning`.

7. **Label the parse stage** during import.

### P2 — the iOS-26 "Liquid Glass" pass

Apply the vocabulary in `docs/uiux/liquid-glass-spec.md` to the **navigation and
control layer only** — header actions, bottom nav, the review progress surface —
never to content cards, list rows or the inventory body. Non-negotiables from
that spec, restated as acceptance criteria:

8. **Glass belongs to the floating control layer.** Bottom nav, the review
   progress bar, sheets and the import/review modals. Content stays on standard
   surfaces.
   *AC:* no glass/backdrop blur is applied to content cards, list rows or the
   inventory table.

9. **Budget ≤3 simultaneous backdrop blurs**; always bound the filter with a
   clip plus `ImageFilter.blur(bounds:)`; never animate the filter itself.
   *AC:* a frame-time trace during scroll stays under 16 ms on the phone
   viewport with the nav and progress bar visible.

10. **Honour accessibility settings.** Reduce Transparency → near-opaque fill and
    no blur; Increase Contrast → stronger rim, higher-contrast text; Reduce
    Motion → cross-fades ≤120 ms, no overshoot.
    *AC:* verified by emulating each setting, not by inspection.

11. **Fix the duplicate font load** (~400 KB) and re-measure cold load.

## 6. Implementation round 2 — what was fixed (2026-09-11)

Verified with `flutter analyze` (clean), `flutter test` (**68/68**), and a real
browser run against a stub proxy on `:8000` (slow enough to observe a 12.5 s
review).

| Fix | Where | Evidence |
|---|---|---|
| **P0-1** Progress moved into the shell, survives the modal | `workspace_shell.dart` `ReviewProgressBar`; modal no longer pops until the first progress event | Bar renders during the run: the 55–175 px band's dominant colour is the bar's `(238,244,233)` sage, returning to `(248,249,246)` after |
| **P0-2** Cancel reachable for the whole run | `ReviewProgressBar` → `cancelReview()` | A tap on it produced **"Review cancelled · 8 units kept."** |
| **P0-3** Bounded concurrency (4) | `AppConfig.reviewConcurrency`, `ReviewRepository._drive` worker pool | 40 units completed in **12.5 s** against a 1.2 s/unit stub (sequential would be ≥48 s) |
| **P0-4** Cap no longer silently drops units | `runReview` clamps instead of refusing; `runSkipped` rides every progress event | Summary reads **"40 units reviewed · 6 verified findings · 23 left out by the 40-unit per-run cap"** |
| **New** Failed units are disclosed | `_onRunFinished` | With the proxy down: **"40 failed and were NOT reviewed"** — previously indistinguishable from a clean "0 findings" run |
| **New** Errors reach the shell | `workspace_shell.dart` error listener | A run error is now a snackbar in the live tree, not a message written into a destroyed modal |
| **New** 390 px overflow | `inventory_tab.dart` badge, `WBadge` ellipsis | `flutter test` caught a pre-existing 14 px `RenderFlex` overflow the browser tour could not see (debug-only stripes, canvas renderer) |

**The bug behind P0-2/P0-4, stated precisely.** The demo selects 63 of 65 units
against a 40-unit cap. Pressing "Review 63 units" ran a guard that *refused* the
run — after the sheet had already been popped. The user got: sheet closes, no
progress, no error, forever. That single path explains "process ko hiện",
"bắt users đợi" and "ko báo cáo tiến độ" at once.

### Instrumentation lesson (recorded because it produced a wrong number)

Twice in this audit my *measurement* was the bug, not the app:

1. A raw `mouse.click(x, y)` on an off-viewport coordinate clicks nothing
   silently — producing a phantom 150 s "hang" that was really a no-op tap.
2. Checking for the progress bar via `body.innerText` missed it, because the bar
   carries an `aria-label` rather than text. It only became visible when
   measured in **pixels**.

Neither Flutter's canvas renderer nor a partial DOM query is ground truth on its
own. Use both, and prefer a pixel or layout measurement when a widget is in
question.

### Left open (honest status)

- **The progress bar exposes no semantics node.** It renders and is tappable —
  a human-style tap on Cancel works — but Flutter emits no `flt-semantics`
  element for it, so it is still invisible to screen readers and to tooling that
  drives the accessibility tree. `container: true` on the `Semantics` was added
  this round but did **not** resolve it; the likely cause is the `Scaffold` +
  nested-scrollable structure. This is a real accessibility defect and remains
  on the list.
- P1 items 5–7 (44 px tap targets, live "Run review" label, parse-stage label)
  are **not** done.
- The iOS-26 "Liquid Glass" pass (P2 items 8–11) is **not** started; the spec is
  written and waiting at `docs/uiux/liquid-glass-spec.md`.

## 6b. Round 3 — corrections to this audit, and one real fix (2026-09-11)

### Correction: the P1-1 tap-target table above is WRONG for icon buttons

The table in §3 P1-1 was built from geometry read out of Flutter's semantics
DOM. That DOM reports the **visible** box, not the **padded tap target**, so
every `IconButton` row in that table understates the real hit area.

Measured directly: `Document information` reports a semantics rect of 34×34, but
a tap **6 px below that box still opens the dialog** — the real target is
Flutter's default 48×48. Re-measuring every icon button in a widget test under
the **real app theme** returns **48×48 for all seven** (`Open navigation`,
`Help & getting started`, `Document information`, `Replace document`,
`Ask document`, `Previous page`, `Next page`).

So: **icon buttons were never below 44 px.** I added a theme-level
`iconButtonTheme` with `minimumSize: 44` this round, then measured with and
without it and got 48×48 either way — a no-op carrying a misleading comment. I
**removed it** rather than leave a fix that fixes nothing.

Two measurement errors of mine are recorded here so the same trap is not
re-entered:

1. I mutated that theme value to 34 and the guard test still passed, which
   should have told me immediately that the theme was not what governed the
   size. (The test also built `MaterialApp.router` **without** `theme:`, so it
   was measuring Flutter defaults, not the app — the tests in
   `workspace_shell_test.dart` have this gap generally.)
2. `getSize()` of the `IconButton` returns the laid-out box, which includes the
   padding — it is the right number; the semantics rect is the wrong one.

**The one genuine hit-target defect was the workflow stepper**, and unlike the
icon buttons it is *not* padded: measured at **80×21** in the browser (the
`Import / 2 Inventory / 3 Findings / 4 Export` row). It is now wrapped in a
`minHeight: 44` container and measures **80×44** in the same probe — same
compact look, full-height touch area.

| Item | Before | After | How verified |
|---|---|---|---|
| Workflow stepper | 80 × **21** | 80 × **44** | Browser semantics probe, before and after rebuild |
| Icon buttons (7) | 48 × 48 | 48 × 48 | Widget test under the real app theme — **no change needed** |

### Also open from earlier rounds

- The progress bar still exposes no semantics node (bar renders and Cancel
  works on a real tap, but assistive tech cannot see it).
- P1 items 5–7 (live "Run review" label, parse-stage label) — not done.
- The Liquid Glass pass — not started.

## 6c. Round 4 — the accessibility gap is structural, not local (2026-09-11)

### What I found

The review progress bar renders and its Cancel button works on a real tap, but
it contributes **nothing** to the semantics tree. I first assumed this was my
widget's fault. It is not — I tested the control case:

| Probed in the real browser | In the accessibility DOM? |
|---|---|
| `Review overview` (inside `navigationShell`) | **yes** |
| `Workspace`, `Online`, `Help & getting started` (**shell chrome, `_TopBar`**) | **no** |
| `Review in progress`, `Cancel`, `Reviewing …`, `outside this run` (**my bar**) | **no** |

A widget test agrees: walking the real semantics tree mid-run yields 83 nodes /
62 labels, and **not one** is the progress bar, Cancel, or any top-bar text. The
`ReviewProgressBar` element and the Cancel widget are both present in the widget
tree (`bar element present: 1`, `Cancel widget present: 1`) — they are simply not
published to semantics.

**Conclusion:** everything rendered as shell chrome *outside* `navigationShell`
is dropped from the accessibility tree, and the progress bar inherits that. It is
a shell-architecture defect, not a widget-local one, so it is **not fixed** and
should not be described as fixed.

### What I did change, and why

- Added `container: true` so the surface has its own node (kept).
- Tried `explicitChildNodes: true` and **reverted it**: it disowns the subtree
  below and Cancel went from one node to none. Shipping it would have made
  accessibility worse while looking like a fix.

### Root cause — narrowed by experiment, not guessed

I ruled out two hypotheses and confirmed the scope:

1. **Not `StatefulShellRoute.indexedStack`.** Read the source
   (`go_router-17.5.0/lib/src/route.dart:1611`): `_IndexedStackedRouteBranchContainer`
   wraps only the *branch children* inside `Offstage`, and the chrome
   (`_TopBar`, `ReviewProgressBar`) sits outside it. So `IndexedStack` cannot be
   swallowing the chrome.
2. **Not local to `ReviewProgressBar`.** I inserted a `Semantics(container: true,
   label: 'PROBE-CHROME-MARKER')` directly into the same `Column`, next to the
   bar. On the next run the marker was **also absent** (`PROBE-FOUND: []`,
   `WORKSPACE-FOUND: []`, 61 labels total). A deliberately-placed marker in that
   column does not reach semantics, so the loss happens above the widget.

**Scope: the entire `Column` that holds the shell chrome contributes no
semantics.** That includes the pre-existing `_TopBar` (probe marker restored
after the experiment; the app is byte-for-byte unchanged).

### What I did change, and why

- `container: true` — kept, so the surface owns a node if the broader issue is fixed.
- `explicitChildNodes: true` — **tried and reverted**: it disowns the subtree
  below and Cancel went from one node to none. Keeping it would have made
  accessibility worse while looking like a fix.

### What remains unproven

The exact mechanism — why a `Semantics` node in that `Column` is not published.
It is above my widget in the composition (`Scaffold.body` → `Row` → `Expanded`
→ `Column`). Fixing it needs a focused experiment outside this feature's code.

## §8 — Round 6–7: Liquid Glass pass, the infinite-height crash, and the 1.6MB font bug

### 8.1 The `RenderErrorBox` masquerading as a layout bug

While applying glass to the progress bar, the widget test failed with
**"A RenderFlex overflowed by 99,214 pixels on the bottom."** That message is
misleading and cost most of a round. The real error, printed further up the
output, was:

```
The following _TypeError was thrown building GlassSurface-[<'review-progress-bar'>]:
Null check operator used on a null value
#0  GlassSurface.build (glass_surface.dart:57:62)
```

Cause: `Theme.of(context).extension<GlassTokens>()!` — the `!` threw whenever a
theme without the extension was in scope (the test built a bare `MaterialApp`).
Flutter answered by substituting a **`RenderErrorBox`**, which reports
`size = (390, 100000)` under unbounded height. The layout never overflowed; a
child had thrown.

**Measurement lesson:** the debugging that worked was walking *down* the render
tree from the failing box, not reasoning about constraints:

```
DIAG bar=Size(390.0, 100000.0)  constraints=BoxConstraints(0..390, 0..Infinity)
DIAG d0 RenderErrorBox size=Size(390.0, 100000.0)
```

`RenderErrorBox` in the tree ⇒ look for a thrown exception, not a layout fault.
Fixed by falling back to `GlassTokens.light()/dark()` instead of asserting.
Guarded by `glass_surface_test.dart` ("survives a theme that has no GlassTokens
registered"), **mutation-checked**: restoring the `!` makes it fail with the
same null error.

### 8.2 Liquid Glass implemented

New files:

- `app/lib/core/theme/glass_tokens.dart` — `GlassTokens` theme extension
  (blur 10/20, saturate 1.8, fill, rim, shadow, radius) + `concentric()`.
- `app/lib/core/widgets/glass_surface.dart` — `GlassSurface`, wired into
  `AppTheme.light()/dark()`.

Applied to the **control layer only**, per the spec (glass on nav/controls,
never on content):

| Surface | Radius | Notes |
|---|---|---|
| `ReviewProgressBar` | 0 | flush under the top bar |
| `_TopBar` | 0 | navigation bar |
| `_GlassTabBar` (new) | 26 | floating capsule |

Accessibility, both required: **Reduce Transparency** (`highContrast`) drops the
blur entirely and raises the fill toward opaque; **Reduce Motion**
(`disableAnimations`) removes the press transition. Flutter exposes no
`disableTransparency` flag, so `highContrast` is the proxy.

No `LayoutBuilder` and no `bounds:` on the blur: this surface is laid out
against unbounded height in the shell, so `constraints.biggest` is infinite
there. `ClipRRect` bounds the composited result, which is what correctness
needs.

### 8.3 Honest limitation: the glass is not truly see-through here

Measured the pixel band under the top bar before and after scrolling the
content: **identical, `(235,237,235)` in both**. The chrome is a `Column` child,
not a layer over the scroll view, so nothing ever passes *behind* the bars and
the backdrop blur samples a flat background. The surfaces therefore read as a
tinted, rim-lit panel — attractive and consistent, but not the real
content-through-material effect of iOS 26.

Layering it properly (scroll viewport owns the full height, bars float above)
is a real refactor of this shell. An attempt was made and reverted: it put the
top bar below the progress bar and referenced an undefined constant. Not worth
risking the P0 progress work for a cosmetic gain; recorded here rather than
overclaimed.

### 8.4 Navigation: the drawer is no longer the only way

The user's complaint "phải bấm menu chưa ổn lắm" was accurate: on a phone all
three destinations were two taps deep behind a hamburger. Added a floating
glass `_GlassTabBar` for narrow screens. Verified in the browser:

```
=== BOTTOM-AREA BUTTONS (y>700) ===
  y= 796 120x48   'Document review Document review'
  y= 796 120x48   'Review history Review history'
  y= 796 120x48   'Syllabus & rubric Syllabus & rubric'
```

## 9. Round 8: the glass is now genuinely see-through

§8.3 recorded an honest limitation: the material was tinted and rim-lit but not
actually translucent, because nothing passed behind the bars. That is now fixed,
and this section supersedes §8.3.

### 9.1 The two real defects behind it

**a) The chrome was stacked, not layered.** The shell was a `Column`
(bar → scroll view → tab bar), so the scroll viewport was clipped *between* the
bars. Nothing could ever cross them, and the backdrop blur sampled a flat page
background. Now the content is `Positioned.fill` and both bars are painted on
top of it, so scrolling genuinely moves content under them.

Reserving the bar height had to move *inside* the scrollable, as content
padding (see `core/widgets/chrome_insets.dart`), rather than as a `Padding`
wrapping the viewport. An outer `Padding` clips content at the bar's edge; scroll
padding only moves the resting position, so content still travels up and behind.

**b) `ContentShell` vertically centred short pages.** The original used
`Center`, which passes *loose* constraints down. A page shorter than the window
shrink-wrapped and was then centred — measured putting the scroll view at
`y=72..772` inside an 844px window. The page floated in the middle with dead
space above it, and the viewport stopped 72px short of both bars, so even a
correctly layered shell could not have shown content behind them.

Found by asserting the *rect*, not by looking at a screenshot: a test that the
scrollable starts at the top of the stack failed with `Actual: <72.0>`. This is
the same lesson as §8.1 — the visible symptom (a page that looks fine, just
slightly airy) did not point at the cause.

Fixed by making `ContentShell` top-aligned and forcing the child's `minHeight`
to the available height when it is finite (so nesting inside another scroll view
is unchanged).

### 9.2 Verification

The metric is the pixel band under the top bar while content scrolls behind it.
An opaque-or-flat panel cannot change; real blur must.

| | band mean under the top bar |
|---|---|
| Before (Column layout) | constant `(235,237,235)` — §8.3 |
| After, at scroll offset 0 | `(229,231,228)` |
| After, scrolled | `(213,218,215)` … `(232,234,233)` |

Content behind the bar visibly blurs — the measurement above is backed by a
screenshot showing card text and the words "document" / "preserved" washed out
behind the top bar, and an inventory row behind the tab bar.

Two structural tests now lock the ordering in, because a screenshot diff cannot
prove which layer is on top:

* `content spans the full height behind the floating chrome` — the scrollable
  must start at the top of the stack and the tab bar must overlap it.
* `scrolling views reserve space for the floating chrome` — the first heading
  must rest clear of the 58px bar.

### 9.3 Two test-harness changes this forced (not product bugs)

Once bars float over content they legitimately intercept touches — iOS behaves
the same way. Two existing tests therefore had to stop tapping under a bar:
`scrollUntilVisible` stops as soon as any sliver is on screen, which measured
parking the target row at `y=8`, i.e. underneath the top bar. The helper
`_scrollToTappable` keeps scrolling until the target is clear of both bars.

Also removed a dead ternary in `glass_surface.dart` (`reduceTransparency ? A : A`)
and lowered `fillLight` 0.42 → 0.34 for a slightly more transparent body now
that the fill is actually compositing over content.


## 10. Rounds 9–15: the shell-chrome gap is closed, and the diagnosis was wrong

§6c and §8.8 left this open with a specific causal claim. That claim was false,
and it is retracted here.

### 10.1 What was actually true

Six rounds of probing measured a real symptom: the top bar, the breadcrumb, the
connection pill and the icon buttons were absent from the accessibility tree,
while the tab bar — a sibling of the same parent — published normally. Isolation
tests then ruled out local `Semantics` misuse, and the conclusion recorded was:

> the cause is upstream of these widgets (shell/route composition), not the
> `Semantics` usage, and not fixable by changing the top bar alone

Everything after "so" was wrong. **It was fixable in the shell, and the layout
refactor in §9 fixed it.** The gap was closed as a side effect of work done for
an unrelated reason (making the glass see-through) — nothing about `Semantics`
was touched to fix it.

The tree, dumped in full with node ids, rects and flags, now reads:

```
#6  rect=0,48   label=[Open navigation]           flags=btn   children=1
#8  rect=0,16   label=[Workspace / Document review] flags=hdr
#9  rect=0,16   label=[Online]
#10 rect=0,48   tooltip=[Help & getting started]  flags=btn
#11 rect=0,48   label=[Document review]           flags=btn
```

In the browser the breadcrumb reaches the DOM as a real `<h2>Workspace / Document
review</h2>` — the `header: true` flag is what chose the heading element.

**No verified mechanism.** It is tempting to say "the clipped viewport also
pruned the chrome's semantics", and that is the shape of a plausible story, but
it is not established — Flutter's semantics culling was not instrumented here.
What is established is only the empirical pair: *before the layout change the
nodes were absent, after it they are present.* Recorded as such rather than as
an explanation.

The lesson generalises the one from §8.1 and §9.1: a negative conclusion that
survives many probes is still only as good as the last layout the probes were
run against. "I tested the widget in isolation and it worked, therefore the bug
is upstream" was the mistake — the isolated test held the layout constant while
the real bug lived *in* it.

### 10.2 A duplicate announcement, found while proving 10.1

Dumping the tree surfaced a second defect: the menu button produced **two**
`role=button` nodes with the same name — the `Semantics(label: 'Open navigation')`
wrapper, and the `IconButton(tooltip: 'Open navigation')` inside it, which was
already named. A screen reader says "Open navigation" twice.

`IconButton(tooltip:)` needs no wrapper; the help button below it has none and
publishes exactly one correctly-named node. Removing the wrapper fixed it. Note
this is the opposite fix to the tab items, which *did* need `excludeSemantics`
because an icon-plus-text composite was doubling — so the rule is "one name per
control", not "always wrap" or "never wrap".

Flutter keeps `label` and `tooltip` in separate fields, so an assertion that
reads only `label` reports the icon buttons as unnamed. The regression test
asserts on the union, which is what a user actually hears.

### 10.3 Status of §8.8's other claim

"`aria-label` is never populated in this build" still holds, and is expected for
CanvasKit: the accessible text is carried in the node's `textContent`, not in
`aria-label`. Probing `[aria-label]` therefore under-reports, which is how
controls that *are* reachable got written off as missing more than once in this
audit. Probe `textContent` and the element's tag.

### 10.4 Guard

`test/workspace_shell_test.dart` → *floating chrome is announced exactly once per
control*: each of the breadcrumb, the connection pill and both icon buttons must
be reachable, and each must appear on **exactly one** node. Mutation-checked:
restoring the duplicate wrapper fails the test with
`"Open navigation" announced 2 times`.

### 10.5 Why the browser probe mis-measured this (instrument error, third instance)

The first browser assertion for §10.1 reported the breadcrumb as absent while
the very next line showed it as `<h2>Workspace / Document review</h2>`. The
probe compared an exact string against **every** `flt-semantics` node's text —
but `textContent` on an ancestor is the *concatenation of its descendants*, so:

* a nested control's text can never equal the control's own name, and
* the same name is counted once per ancestor, i.e. massively over-counted.

That single quirk explains several readings that cost time across this audit:
the giant `YOUR PRE-SUBMISSION COMPANIONDocument review…` "blob" nodes, and the
apparent duplication that was in fact real only for the menu button.

Correct approach, now used: match **per control kind** — buttons by
`flt-semantics[role=button]` text, headings by `h1/h2/h3`, non-interactive
statics by nodes with no `role`. Re-measured with that method, every shell
control is present exactly once:

```
{'menu': 1, 'help': 1, 'tab': 1, 'breadcrumbHeading': 1, 'online': 1}
```

This is the third measurement-instrument error in this document, after
`aria-label` (§8.8) and the semantics box being the visible bounds rather than
the padded tap target (§6b). The recurring lesson: when a probe reports a
*missing* thing that a screenshot shows plainly present, suspect the probe
before the product.

## 11. Rounds 16–20: the transparency had a cost, and paying it

Making the glass genuinely see-through (§9) silently made every bar's backdrop
**variable** — which means the text painted on top of it can no longer assume a
known contrast. This round found and fixed that, plus a pre-existing defect the
new transparency exposed.

### 11.1 Two contrast defects, both measured

**Pre-existing:** `muted` was `#85908A` = **3.13:1** on the canvas. WCAG AA asks
4.5:1 for small text, and this token is used for secondary labels, the
breadcrumb path and timestamps throughout. It failed long before any glass
existed — 82 uses, all on light surfaces.

**Introduced by §9:** with `fillLight` at 0.34 and content passing behind the
bar, the breadcrumb's `ink` text fell to **2.86:1** over a dark backdrop. My own
transparency work had made the text unreadable in a case that did not exist
before.

### 11.2 The fix, chosen by computation rather than by eye

Composing the glass as `white @ fill` over each reachable surface and solving for
AA gave the usable band:

| fill | worst text ratio | see-through swing |
|------|------------------|-------------------|
| 0.34 | 1.97 (fails) | 0.69 |
| 0.66 | 3.71 (fails) | 0.43 |
| **0.78** | **4.58 (passes)** | **0.30** |
| 0.86 | 5.22 (passes) | 0.20 |

`fillLight`/`fillDark` → **0.78**, and `muted` → **#55615A**. Darkening the text
was chosen over raising the opacity further because raising it dulls the effect
the user asked for; 0.78 is the *lowest* value that clears AA, so the glass keeps
as much transparency as correctness allows.

Measured in the browser afterwards, against the real rendered bar:

```
breadcrumb ink    11.55:1  (worst of 13 scroll positions)
muted text         6.14:1
band still swings  229 -> 241 as content passes behind
```

### 11.3 Sixth instrument error — band averaging

The first contrast probe averaged a whole pixel band and reported **2.9:1 for
text that is plainly legible**, at every scroll position including rest. It was
mixing glyph pixels with backdrop pixels, so the "background" it compared against
was partly the text itself. Fixed by sampling a **text-free strip** of the bar for
the backdrop and the darkest 2% inside a glyph region for the ink — which is when
the honest 11.55:1 appeared.

An earlier analytic pass also made the opposite mistake: it treated `ink` as a
possible *backdrop*, asserting against a case that cannot occur (`ink` is a text
token, never painted as a surface). That produced a phantom failure and cost a
cycle. Both errors are the same lesson as §10.5: state what a number is measured
*against* before trusting it.

### 11.4 Guard, mutation-checked both directions

`test/glass_contrast_test.dart` computes WCAG ratios from the live token values
against every reachable surface, in both themes. It has teeth in **both**
directions, verified by mutation:

* `muted` reverted to `#85908A` → fails the plain-canvas assertion.
* `fillLight` lowered to 0.40 → fails with
  `ink on glass over brand is 4.33:1, below AA 4.5`.
* `fillLight` raised past ~0.90 → fails the *translucency* assertion (swing drops
  under 0.15), so nobody can "fix" contrast by making the bar opaque.

A separate Claude Code session is editing this repo in parallel. During this
round it added `required ReviewRun.stage` and left `workspace_models_test.dart`
uncompilable, which briefly blocked verification of unrelated work. The one call

## 12. Round 20: a 44px tap-target defect the whole suite could not see

The final acceptance sweep flagged `Open navigation=40` and `Help & getting
started=40`. Since §6b established that the semantics DOM box is the *visible*
bounds rather than the padded hit area, that reading was treated as suspect and
settled functionally — tapping a grid of points across the bar and watching for
the drawer:

```
before fix   menu hit area: 39 x 37 px   (taps landed only y=10..48, x=16..52)
after fix    menu hit area: 47 x 45 px
```

So this time the rect was truthful. **The tap targets really were below the 44px
platform floor**, on every desktop browser.

### 12.1 Cause

`ThemeData` resolves `materialTapTargetSize` from the platform at construction
time, defaulting to `shrinkWrap` on linux/macos/windows — which renders
`IconButton` at 40x40 instead of 48x48. **Flutter web reports a desktop
platform**, so this is the default for desktop users of this app.

Verified by rendering the same button under all five platforms:

| platform | IconButton | resolved |
|---|---|---|
| android, iOS | 48×48 | `padded` |
| linux, macOS, windows | **40×40** | `shrinkWrap` |

### 12.2 Why 96 tests missed it

The existing test measured `tester.getSize(find.byType(IconButton))` and passed —
because **widget tests default to `TargetPlatform.android`**, where the padded
48×48 applies for free. The test was asserting on a platform the app does not
ship on. This is the same failure shape as the §6a measurement errors, one level
up: not a bad number, but a measurement taken in an unrepresentative environment
and read as a pass.

Fixed by pinning `materialTapTargetSize: MaterialTapTargetSize.padded` beside the
`visualDensity` line, which was already pinned for an identical
platform-defaults-shrink-controls reason.

### 12.3 The guard, and how it was kept honest

`icon buttons stay >=44px on desktop platforms too` builds the theme with
`debugDefaultTargetPlatformOverride = TargetPlatform.linux` **before** calling
`AppTheme.light()`. That ordering matters: `copyWith(platform: …)` after the fact
keeps the already-resolved `shrinkWrap`, so the natural-looking version of this
test would have been a tautology that passed with or without the fix.

Mutation-checked: deleting the theme line fails with
`Expected: padded / Actual: shrinkWrap`. Restored, 96/96 pass.

(Also required clearing the override inline rather than via `addTearDown` — the
binding asserts `debugDefaultTargetPlatformOverride == null` at the end of each
test and runs that check *before* teardown callbacks.)

### 12.4 Seventh instrument error: two-point sampling

The acceptance sweep reported "glass see-through: FAIL" at fill 0.78, comparing
exactly two frames. Both frames happened to sit over light content, so the band
read `(240,241,240)` twice and looked static. Sampling **17 frames in 150px
steps** instead shows a 26-level swing, darkest `(230,235,233)` — the glass is
reacting, and at 0.78 the reaction is subtler than at 0.34, which is exactly the
trade the contrast fix made deliberately.

A binary before/after sample can only detect an effect at the two moments chosen.
For anything driven by scroll position, sample the whole range and report the
swing.

## 14. Round 21+: first paint was network-bound — the CDN build's 87-second tail

### The measurement

Cold-load first paint on the landing page (393×852 mobile viewport, service
workers blocked, 4 loads per variant, measured by `tool/web_first_paint.py` via
`performance.getEntriesByType('paint')[0].startTime`):

| Build | Median first paint | Spread | External requests |
|---|---|---|---|
| CDN (default `flutter build web --release`) | **18,524 ms** | 1.9 s – 87 s | 3 |
| Local (`--no-web-resources-cdn`) | **1,288 ms** | stable | 1 |

**14× faster median**, and the 87-second worst case — the real driver of the
"app khá chậm" complaint — is gone: that tail was CanvasKit and font files
waiting on `fonts.gstatic.com`/CDN latency from Vietnam, a 5× swing entirely
outside the app's control. The local build keeps one external request (the
engine's boot-time Roboto fetch, below).

### The font story, measured to the pixel

The `fontFamilyFallback: [Manrope]` edit is correct for its stated purpose:
`DMSans.ttf` is a 403-codepoint build missing all 44 Vietnamese precomposed
glyphs the app paints; bundled Manrope covers every codepoint. That part was
verified with fontTools against the actual asset files.

But an A/B test (block `fonts.gstatic.com` vs allow, screenshot pixel diff)
found that blocking Roboto still changed **1.7347%** of landing-page pixels —
confined to the two CTA buttons, whose labels ("Import document", "Load the
sample document") are pure ASCII that DM Sans covers. Noise floor on the same
page: 0.0000%, fully deterministic. The fallback was irrelevant: the labels were
never resolving to DM Sans at all.

### Root cause: `ButtonStyle.textStyle` replaces, it does not merge

Three call sites styled buttons with `textStyle: const TextStyle(...)` inside
`styleFrom`:

- `workspace_widgets.dart` — `WButton.primary` (w600) and `.secondary` (w500)
- `app_theme.dart` — the default `filledButtonTheme`

`styleFrom`'s `textStyle` **replaces** the M3 defaults' `textTheme.labelLarge`
as a whole TextStyle — ButtonStyle does not merge it field-by-field. The bare
const styles carry a null family, so the resolved label style had no family and
no fallback; SkParagraph then resolved the glyphs to the engine default, which
is exactly the Roboto woff2 fetched from gstatic. With the CDN build that made
every CTA on the page depend on a request that could hang 87 seconds; with it
blocked, labels fell to a different face — hence the 1.73% diff.

### Fix and re-measurement

All three sites now derive from the theme: `_textTheme(...).labelLarge
?.copyWith(...)` — which carries DM Sans plus the Manrope fallback. Rebuilt,
re-measured: **Roboto allow vs block = 0.0000%** pixel diff, noise 0.0000%.
The gstatic fetch still occurs — it is unconditional at engine boot — but
nothing renders with it anymore; offline or blocked, not one pixel changes.

### Durability

- `tool/build_web.sh` — the only sanctioned web build path: runs
  `flutter build web --release --no-web-resources-cdn` and fails if
  `build/web/canvaskit/canvaskit.wasm` is missing (guards against a silently
  CDN-bound artifact).
- `docs/web-chrome-test-plan.md` — all three build invocations updated to the
  flag.
- `tool/web_first_paint.py` — preserved in-repo so the first-paint and A/B
  numbers above are reproducible.

### Status

Closed. The two independent fixes compose: the build flag removes the network
wait (14× first paint), and the family fix removes the last visual dependence
on the one remaining external request.
