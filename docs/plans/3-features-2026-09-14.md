# Plan — 3 features unblocked by user decision (2026-09-14, round 18+)

User resolved the three decision-wall questions with "build all three".
Two load-bearing facts were **measured before planning**, not assumed:

1. **Vision is live.** `gemini-3.5-flash-lite` (the configured default)
   took a real PNG (a Vietnamese Google Drive error page) over the
   `x-goog-api-key` path and returned an accurate description. HTTP 200.
   The stale models (`gemini-2.5-flash`, `gemini-2.0-flash`) 404 — "no
   longer available to new users". So the default model in `config.py`
   is correct and vision-capable.
2. **The server has no PDF/DOCX parser.** Parsing is entirely
   client-side (`Syncfusion` via `parse_service.dart`); `ReviewRequest.text`
   is "verbatim requirement text parsed by the app" (schemas.py). This
   reorders the three features — see dependency note below.

## Dependency order (this is why I do NOT start with server-side parse)

- **Verdict (10-point, current weights)** needs diagram/cross-artifact
  pass signals → those come from **vision chains**. Build verdict AFTER
  vision produces rows, or it computes on 3 empty components (the exact
  "number nobody can explain" the map section D warned about).
- **Vision chains** are app-side orchestration (render page image →
  `/review` with `image_b64` → parse structured verdict → ledger row).
  The model already sees images on `/review`; the gap is (a) the
  describe-then-judge **two-call** discipline from `vision-prompts.md`
  and (b) wiring a diagram page's verdict into a stable ledger ID.
  This is the highest-value unit AND unblocked → **do it first**.
- **Server-side parse / share-by-link** (F1) is independent and the
  largest lift (new `pdfplumber`/`pymupdf` dependency + a parse endpoint
  that must reproduce the app's 217-page extraction). It does NOT block
  the other two. Park at the end; it may warrant its own planning round
  because it changes the client/server contract.

## Feature 1 — vision chains (DO FIRST)

Goal: for each detector-selected diagram page, produce ledger findings
with stable IDs in the rubric's ID families (ERD/SM/UC/SEQ-CLS/FLOW/
PKG/ARCH/DOC), using the skill's two-call pattern.

Plan:
- `lib/data/checks/diagram_prompts.dart` — port the 6 judge prompts +
  the original describe prompt verbatim from `vision-prompts.md`
  (Vietnamese, so the model reads the same spec the human reviewer
  uses), each returning a strict JSON shape.
- Reuse `PageImageRenderer` (legibility now a known-1.9-dots/pt ceiling
  on A4 — the describe prompt MUST tolerate illegible fine print via the
  `unreadable:[]` field rather than guessing; this directly honours
  trap #3 "model reads wrong then self-confirms").
- `lib/data/services/vision_review_service.dart` — per diagram page:
  call #1 (describe → elements/relations/unreadable), call #2 (judge by
  detected type), map verdicts to `DeterministicFinding`s with
  `ledgerKey`-style stable IDs (`ERD-<n>`, `SEQ-CLS-<n>`). Zoom-recheck
  of every 🔴 is a documented follow-up, not silently skipped — record
  unreadable verdicts at a lower confidence instead of asserting.
- Mock provider gains a `diagram` branch so this is testable without
  burning quota (testing-strategy: L3 with fake, L4 smoke once).

Risks: quota (bounded: one doc = 14 diagram pages × 2 calls ≈ 28
calls, each cached); false confidence on illegible text (mitigated by
`unreadable` + not promoting to 🔴 without zoom).

## Feature 2 — 10-point verdict (AFTER feature 1 produces data)

- Pure function `computeVerdict(syllabusSectionPass, diagramPass,
  crossArtifactPass, traceabilityPass, redFlowErCount)` implementing
  rubric mục E: floor 5 (rubric A complete) +2 diagram +2 cross-artifact
  +1 traceability, −1 each 🔴 FLOW/ERD affecting real data.
- Inputs come from the ledger rows feature 1 produces (cross-artifact
  matrix already exists: `crossArtifactName`; traceability needs the
  FK/seq chains). Until feature 1 is in, the components are honest
  `null` = "not assessed", and the verdict renders as "X/10 (partial —
  N components unassessed)" never a fabricated total.
- Bump `prompt_version`/rubric `v2`→`v3` ONLY if weights change; the
  `test_rubric_pins.py` tripwire enforces that.

## Definition of Done per feature (testing-strategy levels)
- L1 pure logic (prompt builders, verdict function): unit tests that
  fail when the mapping is wrong.
- L3 fakes (mock diagram branch, scripted LLM): service tests assert the
  two-call order + ID stability, no real network.
- L4 smoke: ONE real vision call proving the wire contract, once, with
  the response captured as a fixture (as the live PONG/probe above).
