1. Turn a design and a handoff specification into a working Flutter app, and measure how
closely the result matches the design.
2. Structure a Flutter app with the MVVM pattern and Provider or Riverpod, keeping
business logic out of the UI.
3. Integrate Firebase Authentication (Google Sign-In), Cloud Firestore, Cloud Messaging,
Analytics, Crashlytics and Remote Config.
4. Secure user data with Firestore Security Rules and store generated files in an object
storage service without exposing secrets in the app.
5. Use AI coding tools responsibly: verify what they generate, and record what you
accepted, changed or rejected.
6. Automate end-to-end tests with an AI testing agent (MobAI), review the tests it
writes, and judge whether a healed test is still a valid test.
7. Use AI-assisted code review to find defects and decide which findings to act on.
3. Task and scope
Build the mobile app you designed in Lab 2 as a working Flutter application for Android.
The app must:
Implement all screens of your Lab 2 final UI (at least 8 screens) with real navigation.
Make all 3 Lab 2 user flows work end to end, including the error or recovery path.
Use Cloud Firestore as its backend, so that data is created, read, updated and deleted
for real and belongs to the signed-in user.
Integrate the Firebase services listed in section 6.
Follow your own design system: colors, typography, spacing and components come
from the Lab 2 tokens and component library.
Design changes. A working app always reveals problems in a design. You may change the
design, but every change must be recorded in docs/design-change-log.md  with the
reason, and Figma must be updated or annotated to match. Two changes are expected
and do not need justification beyond a log entry: a Login screen (Google Sign-In) and a
Profile screen, if your Lab 2 design does not already have them.
Out of scope. iOS builds, custom backend servers, payments, and features that were not
in your Lab 2 design (except those required by this lab).

6.2 Authentication
Use Firebase Authentication with Google Sign-In. Users can sign in with a Google account,
see their profile information (picture, name, email), and sign out. Unauthenticated users
can only see the Login screen. On Android you must register your debug signing
certificate (SHA-1) in the Firebase project for Google Sign-In to work.
6.3 Data with Cloud Firestore
Store the main entity in Cloud Firestore, scoped to the signed-in user (for example
users/{uid}/items ). Use at least two collections or subcollections.
Implement create, read (list and detail), update and delete for the main entity.
Use at least one query with filtering or sorting, and at least one real-time listener so
that the UI updates when data changes.
Provide seed data or a way to create test data, so that every screen can be
demonstrated.
Write Firestore Security Rules so that a signed-in user can read and write only their
own data. Keep the rules in firebase/firestore.rules  and deploy them. Test mode
rules (open to everyone) are not accepted in the final submission.

6.5 Push notifications (FCM)
The app receives push notifications sent from the Firebase console, both when it is open
and when it is in the background. It requests the notification permission on Android 13
and above, shows received notifications in a Notification Center list (inside Profile or as a
screen in your design), and opens the relevant screen when a notification is tapped.
Notifications should be relevant to your topic (for example a reminder or an alert).
6.6 Remote Config
Fetch at least two Remote Config values, with in-app default values, and use them to
change real app behavior (for example a limit on displayed items, a feature switch, or a
banner message). Show the current values in Profile for demonstration. Evidence: change
a value in the Firebase console, publish, and show the app changing.
6.7 Crashlytics
Integrate Crashlytics. Provide a demonstration control (for example in Profile) that
records a handled exception and another that causes a test crash. Evidence: both appear
in the Crashlytics dashboard.
6.8 Analytics
Track user activity with Firebase Analytics. Write an event plan in docs/analytics-
plan.md  (event, trigger, parameters, related Lab 2 flow) and implement it. Event names
use lowercase letters, digits and underscores, and are at most 40 characters.

8. Design fidelity check
Compare your app with your Lab 2 design and report the result honestly in
docs/fidelity-check.md . This is not a search for a perfect match; it is evidence that you
know where the app differs from the design and why.
1. Screen comparison. For every screen, place the Figma screenshot next to an app
screenshot taken on the same size (360 × 800 dp) and list each difference with a
reason (design problem found, technical limit, or mistake not yet fixed).
2. Token check. Colors, text styles, spacing and corner radius come only from
lib/theme/ . Search the code for hard-coded color and size values outside the theme
and list each exception with a reason.
3. Component check. Every component from your Lab 2 library exists as one reusable
widget with the same variants and states, and screens use it instead of re-building it.
4. State check. Loading, empty and error states from Lab 2 appear on the app screens,
shown with screenshots of real situations (for example airplane mode for the error
state).
5. Accessibility check. Repeat your Lab 2 checklist on the running app: contrast, touch
target of at least 48 × 48 dp, and layout at 360 dp and 412 dp widths.
6. Handoff gaps. In docs/handoff-gaps.md , list every place where your own flutter-
handoff.md  was unclear, incomplete or wrong, and how you resolved it. This is
feedback on your Lab 2 specification and is graded as part of the process.

Rules for the tests
Read every script the agent writes and edit it. An assertion that only proves the taps
happened is not a test; each test must check a visible outcome.
Document the starting state (account, seed data) so that each test can be re-run from
a clean state. Never commit account credentials.
Use a separate Google account created for testing. Google may show extra screens
during sign-in; handle them in the script, or, if a step cannot be automated reliably,
keep a documented manual step and explain why.
Store scripts in mobai_tests/  and explain each test briefly in docs/test-report.md .
Two exercises that check you understand the tests
1. Healing. Make a small deliberate UI change (for example rename a button label), run
the affected test, let the tool patch the script, and record the difference. Decide
whether the patch only updated how the element is found, or whether it weakened
what the test checks.
2. Catching a real bug. Introduce a real defect (for example make saving an item silently
do nothing) and show that a test fails. Then remove the defect and show it passes. A
suite that heals itself around a real bug is worse than no suite.
Evidence. The .mob  files in the repository, screenshots or logs of a full run, a results table
(pass or fail per test), the two exercises above, and a short explanation of each test.
Tool note. MobAI is a third-party product whose features and free-tier limits can change.
If you cannot use it, tell the lecturer before switching to another tool.
