## 2. (0) Mobile / web regression — the P0 question

This was checked first and hardest, because P1 edits `core/theme/app_theme.dart`
and four widgets shared with phone and web.

Measured (all in `qa_p1_adversarial_test.dart`, group `(0)`):

* **`AppTheme.light()` and `AppTheme.dark()` on Android are byte-identical to
  Flutter's own defaults.** Not "not equal to the desktop value" — equal to
  `ThemeData(colorScheme: <same scheme>, useMaterial3: <same>)`, for
  `hoverColor`, `focusColor`, `scrollbarTheme.thumbVisibility`, `.thickness` and
  `.thumbColor`. The weaker form the engineer used would also pass for any
  *wrong* value that happens to differ from the desktop one.
* **`TargetPlatform.linux`: `AppPlatform.isDesktop == false`** and every theme
  value is still the default. Linux is correctly *not* a desktop target, which
  is what keeps `test/workspace_shell_test.dart`'s linux tap-target assertions
  measuring what they think they measure.
* **A real `InventoryTab` on Android contains zero `Scrollbar`s.** The
  framework adds one only on linux/macOS/windows
  (`MaterialScrollBehavior.buildScrollbar`, verified in
  `packages/flutter/lib/src/material/app.dart:857`), and the theme overlay is
  applied only on macOS/windows — so nothing leaks onto phones.
* **No focus ring on load** (nothing is focused, nothing is painted).
* **A real secondary-button click on Android opens no menu** (§6).

No P0. The "do not regress mobile/web" commitment holds for everything that can
be measured in a test.

Not executable: the `kIsWeb` branch. `flutter test` cannot make `kIsWeb` true.
It is safe **by construction** — `AppPlatform.isDesktop` is
`!kIsWeb && (macOS || windows)`, and `AppPlatform.isWeb` is checked first in
`formFactor` — so every desktop affordance is off in a browser. Flagged as
D-05 only because it is verified by reading, not by running.

## 3. (1) P1-A — scrollbars

**The engineer's claim is correct, and I confirmed it against the framework.**
`MaterialScrollBehavior.buildScrollbar` (material/app.dart:857) already wraps
every *vertical* `ScrollView` in a `Scrollbar` on linux, macOS and windows, and
that `Scrollbar` leaves `thumbVisibility` null so it resolves from the theme.
One theme entry therefore is the feature, and a hand-wrapped `Scrollbar` would
indeed have produced two thumbs.

What I measured beyond that:

* **Nested scroll views get one bar each, never two** — a `Column` of two
  `ListView`s on macOS yields exactly `2` `Scrollbar`s. This is the assertion
  that would catch a double wrap in a real screen; a single synthetic
  `ListView` cannot.
* **Windows behaves identically to macOS** (1 bar, thumb resolves visible).
* The bar's own `thumbVisibility` is `null` and the resolved theme value is
  `true` with **no hover at all** — which is the actual requirement.
* **Linux keeps the framework bar in its hover-only default** (theme untouched).

**Gap D-02 (P3):** horizontal `ListView`s get **no** scrollbar. This is not the
implementation's fault — `buildScrollbar` returns the child untouched for
`Axis.horizontal`, so no theme change can reach them. Documented, not fixed.

## 4. (2) P1-B — hover

**The engineer's diagnosis is correct and I verified the mechanism, not just the
story.** `WPanel` really is an opaque `DecoratedBox`
(`workspace_widgets.dart:160`, `color: colors.surface`), and `AppInkWell` puts a
`Material(type: MaterialType.transparency)` **inside** it — asserted as
*descendant of the opaque panel* and *ancestor of the `InkWell`*, because the
direction is the whole fix. Ink painted on a Material that is a descendant of
the panel is painted above the panel's colour; ink painted on an ancestor
Material is covered by it.

`MetricCard` was also on the list of touched widgets, and the engineer's note
there is accurate: the original `InkWell(WPanel(...))` order would have made the
fix a no-op. But **inverting the two introduced a regression — see D-01.**

### D-01 — `MetricCard` tap target and hover area shrank by 32px (P2, source)

**File:** `app/lib/features/workspace/view/workspace_widgets.dart:311-313`
(`MetricCard.build`)

```
return WPanel(
  padding: const EdgeInsets.all(AppSpacing.lg),   // 16
  child: AppInkWell(  ...
```

Before P1 the `InkWell` **wrapped** `WPanel`, so it covered the card edge to
edge. Now the `InkWell` sits **inside the panel's 16px padding**. Measured on a
240×160 card: panel `240×160`, ink `208×128` — 32px lost in each dimension.

Two symptoms, one cause:

1. **Mobile / touch:** the tappable region is ~30% smaller. `MetricCard` is used
   with a real `onTap` at `document_review_view.dart:189`, on a 2-column phone
   grid. It stays above the 44px floor, so this is not a hard failure — but it
   is a behaviour change on a platform P1 promised not to touch.
2. **Desktop:** the hover wash is a rounded rectangle floating 16px inside the
   card, with its own 12px corner radius offset from the card's — the ink no
   longer fills the surface it is supposed to highlight.

**Fix, verified by me (test goes green, no other test breaks):**

```dart
return WPanel(
  child: AppInkWell(
    onTap: onTap,
    borderRadius: AppRadius.boxMd,
    child: Padding(
      padding: const EdgeInsets.all(AppSpacing.lg),
      child: Column(/* … unchanged … */),
    ),
  ),
);
```

Moving the padding *inside* the ink restores the full-card tap target and makes
the hover wash fill the card, while keeping the ink inside the panel (so the
P1-B fix still works). I confirmed this locally and then **reverted it** —
source changes belong to the engineer (§11).

**Status: FIXED by the engineer and re-verified by QA (round 2).** The engineer
applied this change with a comment explaining *why* the padding belongs inside,
and added their own guard
(`p1_hover_focus_test.dart` › `MetricCard` › *the tappable area still covers the
whole card*, `expect(getSize(InkWell), getSize(MetricCard))`). I mutation-tested
both that guard and mine (§12): each catches the defect.

## 5. (3) P1-C — focus ring

Measured, not assumed:

* **No new Tab stop.** With a plain `InkWell` and with an `AppInkWell` in the
  same `[TextField, row, TextField]` subtree, `FocusScope.traversalDescendants`
  returns **4 nodes in both cases**. `AppInkWell` does add one node to the tree
  (`descendants` goes 4 → 5) — that is how it observes focus — but the added
  node is `skipTraversal == true` **and** `canRequestFocus == false`, and it is
  absent from `traversalDescendants`. Order and count are untouched.
* **A mouse click does not paint the ring.** With a `PointerDeviceKind.mouse`
  gesture, down + up over the row, `_rings` stays empty. This is the desktop
  convention and it holds here.
* **Positive control in the same test:** immediately after, keyboard
  `requestFocus()` on the same tree paints exactly one 2px uniform ring. So the
  empty result for the mouse is a real answer, not a blind spot in the filter.
  (My first filter was genuinely blind — it counted every bordered
  `DecoratedBox`, and inventory rows and `WBadge` all have borders. That was a
  bug in my test, fixed.)
* Ring removal on unfocus is covered by the engineer's test.

## 8. (5) P1-E — macOS window autosave (code review; this machine has no `xcodebuild`)

`app/macos/Runner/MainFlutterWindow.swift`:

* `setFrameAutosaveName("MainWindow")` is called **before**
  `setFrameUsingName("MainWindow")` — correct; reversed, the stored frame would
  be dead code while the app still looked right in a screenshot.
* The P0 default frame (1280×860 + `center()`) is **inside** `if !setFrameUsingName(...)`,
  so a stored frame wins and the default applies only on first launch.
* `minSize = 960×680` is set **before** the restore, so a stored frame smaller
  than the minimum is clamped by AppKit rather than by a Dart rebuild.
* **The autosave name is unique and stable**: `MainMenu.xib` declares exactly one
  `<window … customClass="MainFlutterWindow">`, so `"MainWindow"` cannot collide
  with another window. The preference key it writes
  (`NSWindow Frame MainWindow`) is constant across launches.

Observations (P3, no action recommended now):

* **D-03 — the test was weaker than it looked.**
  `p1_window_autosave_test.dart` matches source text, so it could not detect
  `setFrame` being moved *outside* the `if !` block — the one edit that would
  silently break the feature while leaving every ordering index in the right
  relative order. **Fixed by the engineer in round 2** and mutation-tested by me
  (§12): the guard now asserts `setFrame` lies between `if !self.setFrameUsingName`
  and the first `}` closing that block.
* **D-04 — a restored frame can land off-screen** if the display configuration
  changed (external monitor unplugged). AppKit's `setFrameUsingName` does not
  guarantee on-screen placement. Fixing it properly needs display-aware
  clamping, i.e. the `window_manager` dependency this project has deliberately
  ruled out.

## 9. (6) P1-F — transparent title bar, deliberately skipped

**Confirmed: the reasons are sound and they are documented.** §2 of
`docs/desktop/P1-DESKTOP-POLISH-2026-09-12.md` lists all three, and the PRD
status table marks P1-9 as ❌ with a pointer to that section.

My independent read of the three:

1. *Cannot measure the 72px inset without a macOS build.* Valid — and the
   failure modes (a 72px hole, or traffic lights on top of the breadcrumb) are
   worse than the status quo.
2. *`isMovableByWindowBackground` competes with Flutter's mouse handling.*
   Valid and underrated. Whether `NSView.mouseDownCanMoveWindow` defers to the
   Flutter view is genuinely not determinable from here, and a scroll/drag
   regression costs far more than the aesthetic.
3. *`.fullSizeContentView` changes frame↔content-size relations.* Valid — it
   would disturb the P0 `minSize`/`setFrame` work this same milestone pinned.

Agree with the recommendation to do it as one commit on a machine with Xcode,
with the top bar's leading padding gated on a new `AppPlatform.isMacOS` so
Windows never receives it.

Also confirmed documented: P1-1 (drag & drop), P1-2 (native menu bar), P1-4
(multi-window) and P1-10 (split view) are explicitly out of scope with reasons,
and P1-5 on Windows is called out as a follow-up that needs a Windows CI runner.
