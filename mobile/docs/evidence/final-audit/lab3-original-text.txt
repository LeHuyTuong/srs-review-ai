In this lab you build the app you designed in Lab 2 as a cloud-enabled Flutter product:
users sign in, the app reports what they do and how it fails, it can be reconfigured without
a new build, and its critical flows are checked by automated tests. You are graded on a
working app and on the evidence that it works. The product (features, Firebase
integration, architecture, UI) is worth 6 of 10 points; the engineering process (testing,
code review, presentation slides and demo video, backed by a final report) is worth 4.
This handout states what must be true of your app, not which screens to build: those
come from your Lab 2 design. Each requirement names its evidence; work that cannot be
shown is graded as missing.

2. Learning outcomes
After this lab you can:
1 . Implement a Figma design (flows, design tokens and components with states) in
Flutter, so the built app matches its specification.
2. Structure a Flutter app in MVVM so that UI, state, business logic and external services
can be changed and tested independently.
3. Integrate a cloud backend (Firebase) for identity, file storage, messaging and remote
configuration, and handle each service's failure cases.
4. Design an analytics event plan that answers product questions, and instrument the
app to record it.
5. Make crashes and handled errors observable in production.
6. Write a test plan, automate end-to-end tests of critical user flows with an AI testing
agent, and judge whether its results can be trusted.
7. Use AI to review code, then judge each finding and act on it with a stated reason.

Build the app you designed in Lab 2 (AI-Assisted UI/UX Design) as a working Flutter app
on Firebase. Your Lab 2 deliverables are the specification: the persona and success
criterion, the information architecture and the 3 user flows, the design system and
components, and handoff/flutter-handoff.md . Your final app must:
Implement every screen on the Lab 2 Final UI page (at least 8) and every Lab 2 flow
end to end, including its alternative and error/recovery path, as they run in the Figma
prototype.
Build the Lab 2 design system in code: tokens as a ThemeData  ( ColorScheme ,
TextTheme , spacing and radius constants) and each Lab 2 component as one reusable
widget with its states (section 5).

Rules that are checked in grading:
No widget calls http , FirebaseAuth.instance , FirebaseAnalytics.instance  or any
other SDK directly. Every external call goes through a service.
Business logic (filtering, ranking, aggregation, validation) lives in ViewModels or
services, never in build()  methods.
Each data-loading screen has an explicit state model (for example a sealed class or
enum for loading, empty, error, data) owned by its ViewModel.
Services are injected (through Provider/Riverpod), so a ViewModel can be tested with
a fake service.
docs/architecture.md  must contain: the folder structure with one line per folder, a layer
diagram (Mermaid is fine), one sequence diagram for a full flow (for example: search →
API → ViewModel → chart), and a table of ViewModels with the services each one uses.
Suggested structure: lib/  with models/ , services/ , firebase/ , viewmodels/ ,
screens/ , widgets/ , utils/ . You may change it if architecture.md  explains why.

Design system in code
The Lab 2 design system is part of the architecture, not decoration. Build it from the two
mapping tables in your flutter-handoff.md :
Tokens live in one place ( lib/theme/ ): colours in a ColorScheme , text styles in a
TextTheme , spacing, radius and elevation as named constants. Widgets read them
from the theme; a hard-coded colour, font size or padding in a screen is a defect.
Each Lab 2 component (button, text field, card, navigation, app bar, dialog, loading,
empty and error state) is one reusable widget in widgets/ , with its Lab 2 variants and
states as parameters. Screens use these widgets, not one-off copies.
The Lab 2 accessibility checklist must still hold in the built app: contrast, touch targets
of at least 48 dp, body text of at least 14 sp, no meaning by colour alone, layout checked
at 360 dp and 412 dp.

7. Automated E2E testing with Google ARTEMIS
You must test, automatically, every flow a user depends on, using Google ARTEMIS: an
open-source (Apache 2.0) AI agent that drives a real Android device or emulator from
natural-language test instructions. Because the tester is itself an AI, you are graded on
how well you make its results trustworthy, not only on how many tests pass.
Setup. Python 3.12+, uv  and ADB (the ARTEMIS start script installs ADB, scrcpy and
FFmpeg); an API key for a supported multimodal model (Gemini, Claude, GPT-4o or Qwen-
VL). Use the Flash profile (about 3–5 s per step) for regression tests and the Pro profile
only for the exploratory session. ARTEMIS is new and changes quickly: pin the commit you
use in README.md .
docs/test-plan.md  must contain (template in Appendix B):
A list of the critical flows of your app, each mapped to the screens it uses.
At least 10 test cases, each with an ID, a precondition, the natural-language instruction,
the expected result and the flow it covers.
Coverage of: each Lab 2 user flow end to end, including its alternative and error paths;
plus sign-in, the main search or primary action, each top-level tab, each kind of detail
screen, export and upload, Remote Config values on screen, and sign-out.
At least 1 error-path test (for example: a search with no results shows the empty state,
or no network shows the error state with a retry).
At least 1 native interaction (for example: the Google account picker, the notification
permission dialog, or opening a push notification from the notification shade).
1 exploratory session in the Pro profile (15–30 minutes, unscripted) and a list of the
issues it found.
Rules for the tests:
Each test is a pytest  function that sends one instruction through the ARTEMIS
Python SDK ( ArtemisClient ). The instruction states the starting point, the steps and
exactly what must be visible at the end. "Check that the app works" is not a test.
Assert on what the agent reports, not on status == "SUCCESS"  alone: ask it to return
the values it sees (result count, journal name, Remote Config value) as structured
output and compare them with expected values.

Run every test at least 3 times and report the pass rate. A test that does not pass 3 of 3
is flaky: find out whether the cause is the app, timing or an ambiguous instruction, and
record the fix.
Add Semantics  labels to key Flutter widgets (buttons, list items, charts). ARTEMIS
reads the accessibility tree first and falls back to vision for custom Flutter UI, so labels
make tests faster and more reliable, and the app more accessible.
Tests do not depend on each other's order; each one starts from its stated
precondition.
Use a dedicated Google test account for sign-in, never a personal one. Keep its
credentials and your model API key out of the repository (environment variables).
At least one test also checks that its analytics event was logged (Analytics debug
mode on; check the run's Logcat capture or DebugView).
Example shape of one test:
async def test_tc02_search_shows_results(artemis):
    result = await artemis.run(
        "Open the Journal Trend Analyzer app, signed in. On Home, search for 
"
        "'machine learning'. Verify a publication list and a trend chart are 
"
        "shown, and report the total publication count displayed."
    )
    assert result.status == "SUCCESS", result.error
    # then assert on the reported count, e.g. > 0
Place tests in e2e_test/  with a conftest.py  that creates the client (device serial,
profile), grouped by feature (for example test_auth.py , test_search.py ,
test_detail.py , test_export.py , test_profile.py ).
Evidence: the command used to run the suite; the trace ID, screenshots or replay of each
run; a results table (test ID, runs, pass rate, average time); an explanation of every flaky,
failed or skipped test; and the exploratory session report.
